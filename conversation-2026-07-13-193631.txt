  A) Volume/duration deltas — is drift computable?

  Yes, but only indirectly and only for the final submission (not autosave 
  drafts alone).

  - The wizard reducer (useValidationWizard.js) stores per-workflow decisions as
  { kept, volumeAnswer, volumePct, durationAnswer, durationPct } — i.e., the
  delta/answer, not the original modeled number, and not the adjusted absolute
  number either.
  - At finalize (validate-finalize.js:104-126), the server re-reads the
  pre-adjustment workflow (current.monthlyVolume, current.minutesPerItemBefore)
  from state.workflows (built from the report's existing state_data), applies
  volumePct/durationPct, and writes the adjusted values back into state_data —
  overwriting the original.
  - However, reports.validation_data.workflowDecisions (written at finalize,
  validate-finalize.js:149-160) permanently retains the exact
  volumePct/durationPct/volumeAnswer/durationAnswer per workflow name. Since
  validate-finalize.js computes adjusted = round(original * (1 + pct/100)), you
  can algebraically back out original ≈ adjusted / (1 + pct/100) by combining
  validation_data.workflowDecisions with the post-finalize state_data — rounding
  makes this reconstruction only approximate for small values.
  - Original modeled value is not stored verbatim anywhere post-finalize — it's
  overwritten in state_data. If you need exact drift (not reconstructed), you'd
  need to snapshot state.workflows (or just monthlyVolume/minutesPerItemBefore)
  into validation_data before the patch step at validate-finalize.js:104.
  - The autosave draft (validation.js, PATCH) only stores the same decision
  shape (workflowDecisions, not before/after absolutes) into
  reports.validation_data, merged shallowly — no snapshot of the baseline
  either.

  B) Workflow add/remove — is the action itself recorded?

  Remove: Yes, indirectly — decisions[name].kept = false is set by toggleKeep
  (ConfirmWorkflowsStep.jsx:105, reducer TOGGLE_KEEP) and persists in
  workflowDecisions inside validation_data. So you can tell which named
  workflows were removed (kept === false) vs. kept. No event/log entry is
  written for the toggle itself — no timestamp, no "why."

  Add: Weaker. Clicking "+ Add a workflow we missed" sends a freeform chat
  message to /api/roi-agent (mode chat) which may call the add_workflow tool
  (agent.ts:1225). This mutates state.workflows live via appendWorkflow. The
  only persistence of "an add happened" is:
  - A generic chat_message_sent event row in events (no indication it resulted
  in add_workflow specifically).
  - The wizard's REBASE_FROM_CHAT action resets baseline to the new workflow
  list — the previous baseline is discarded from wizard state (no diff retained
  client-side).
  - At finalize, any workflow present in state.workflows but not a key in
  workflowDecisions is just marked userValidated: true

  this originally" vs. "user added this via chat mid-wizard."

  Conclusion: neither add nor remove has a dedicated audit trail today. Remove

  reconstructable at all from stored data — you'd need to add explicit event

  ConfirmWorkflowsStep's toggleKeep) to capture it.
